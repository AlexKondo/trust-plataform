## 3. Implemented

### 3.1 Design decision: `ServiceRequest` as a small, separate aggregate — not a `MarketplaceListing` variant

The mandate explicitly forbids naming this "Order" or "Listing" (both taken) and asks for the minimum-safe addition. `ServiceRequest` (file `domain/entities/service-request.ts`) is a new aggregate root, deliberately smaller than `MarketplaceListing`:

- **No draft/publish two-phase lifecycle.** A `ServiceRequest` is never publicly navigable (§3.7) — only its own owner ever reads it — so there is no reason to model an incomplete intermediate state the way `MarketplaceListing.createDraft()` does for a publicly-browsable anúncio. It is created complete and immediately `OPEN`.
- **Status machine**: `OPEN -> MATCHED -> {CLOSED, CANCELLED}`, plus a **derived, never-persisted** `EXPIRED` — the exact same "derived expiry, no scan job" idiom `MarketplaceOffer.effectiveStatus()` already uses (`SERVICE_REQUEST_TRANSITIONS`/`SERVICE_REQUEST_STATUS` in `marketplace-types.ts`). `MATCHED` is reached the first time the Member engages any eligible Partner and is **idempotent** — engaging a second/third Partner afterward is not an error and does not re-fire the transition; it signals "at least one contact happened," not exclusivity (exclusivity remains `MarketplaceListing.reserve()`'s job at offer-acceptance time, untouched by this IP). `CLOSED`/`CANCELLED` are terminal, mutually exclusive, and mirror `MarketplaceOrder.cancel()`'s "mandatory reason" convention for cancellation.
- **Single mutation gate**: `transitionTo(target, now)` throws `ServiceRequestTransitionException(from, to)` on any non-adjacent jump — literally the same `canTransitionTo`/`transitionTo` shape as `MarketplaceOrder`, reused as a pattern (not a base class extraction — the mandate's "no opportunistic refactor" rule (§5.3 of `00_READ_FIRST`) was read as forbidding introducing a new shared base class across aggregates that don't already share one).

New files: `apps/api/src/modules/marketplace/domain/entities/service-request.ts` (329 lines) + `service-request.spec.ts` (139 lines, 12 unit tests — creation, budget validation, idempotent `markMatched`, derived `EXPIRED`, terminal-state transition guards, ownership guards, mandatory cancel reason, `restore()` round-trip).

### 3.3 `DiscoverServiceRequestMatchesUseCase` — deterministic, no-AI eligibility

`application/usecases/discover-service-request-matches.usecase.ts`. This is the "deterministic eligibility/matching foundation" the spec asks for, and it is intentionally **not a new query or index**: it calls `MarketplaceListingRepository.search()` — the exact repository method `SearchListingsUseCase` (MRK-004) already uses — with criteria derived from the `ServiceRequest`: `categoryId`, `listingType: SERVICE`, `location: request.locationLabel`, `allowedSellerLevels` (via `levelsAtOrAbove`, reused unchanged, including its "unknown level → empty page, not an error" convention), sorted by `trust_score` (reputation-first, deterministic, explainable — the exact ordering MRK-004's own `sort=trust_score` already produces). Each result is annotated with `alreadyEngaged` (cross-referenced against `listEngagements()`) so the UI can show the Member which Partners were already contacted for this request. Zero AI/embedding/LLM call anywhere in this path — confirmed by construction (it is a parameterized call into pre-existing, non-AI repository code) and by the absence of any new dependency in `package.json`.

### 3.4 CAS repository method: `markMatchedIfOpen`

`infrastructure/persistence/drizzle-service-request.repository.ts`. `UPDATE service_requests SET status='MATCHED', matched_at=? WHERE id=? AND status='OPEN' RETURNING id` — the same compare-and-set idiom as `saveWithExpectedStatus`/`closePauseIfOpen`/IP-007's `markReadyForReleaseIfInCustody`. Returning `false` on a lost race is not an error (§3.1) — the calling use case (§3.5) simply proceeds without re-publishing `ServiceRequest.Matched`. `saveEngagement()` uses `.onConflictDoNothing()` **with no target** on `service_request_engagements` — following IP-007 §10.4's own documented fix (a target-less `ON CONFLICT DO NOTHING` suppresses a conflict on *any* unique/exclusion constraint on the table, not just a named one) applied proactively here from the start, not discovered as a bug during this IP's own testing.

### 3.5 `EngageServiceRequestUseCase` — links the request to the existing conversation/offer lifecycle

`application/usecases/engage-service-request.usecase.ts`. This is the piece the mandate most explicitly asked to get right ("reuse `contact-listing-owner.usecase.ts`'s shape... rather than inventing a parallel conversation-creation path"). It calls `ContactListingOwnerUseCase.execute()` **unmodified** (confirmed: `git diff` on that file is empty) to create-or-reuse the `MarketplaceConversation` and its first/next message — all existing ownership/availability/dedupe rules apply exactly as they do for a listing-page contact. On top of that, in a **separate** transaction (§11.4 explains why separate is safe), it:

1. CAS-transitions the request `OPEN -> MATCHED` only on the very first engagement (§3.4), capturing `markMatchedIfOpen`'s own **boolean return value** (`casWon`);
2. Inserts a `service_request_engagements` row (`UNIQUE(service_request_id, listing_id)`) recording which conversation originated from this request/listing pair;
3. Publishes `ServiceRequestEngagement.Created` always (when the row is genuinely new) and `ServiceRequest.Matched` **only when `casWon` is `true`** — i.e. only for whichever concurrent caller actually won the database-level CAS, never for a caller that merely read `OPEN` before the race window.

**Correction applied after independent Diff Review (§F/§J.1 of `IP-003-DIFF-REVIEW.md`)**: the first version of this use case gated the `ServiceRequest.Matched` publish on a stale pre-transaction snapshot (`wasAlreadyMatched`, read via `findById()` before `ContactListingOwnerUseCase` and the transaction even ran) instead of `markMatchedIfOpen`'s actual return value. Under genuine concurrent engagement (two calls against different listings, both reading `OPEN` before the race window), both would independently compute `wasAlreadyMatched = false` and both would enqueue `ServiceRequest.Matched`, even though the persisted `service_requests.status` correctly transitioned only once — a real, reproducible double-publish, not merely a theoretical one. Fixed to capture and gate on `casWon` (`markMatchedIfOpen`'s own return value), the exact idiom `release-funds.usecase.ts` (IP-007) already uses for its own two CAS calls (`const marked = await ...; if (!marked) { ... }`). See §11.6 for the full account, §9 for the corrected invariant claim, and §10 for the new test coverage (a unit race-loser test plus an `outbox_events`-row-count assertion added to the existing e2e race test) that would have caught this and now passes.

Reengaging the same listing reuses the same conversation (`ContactListingOwnerUseCase`'s own dedupe) and the same engagement row (`onConflictDoNothing`) — mirrors MRK-006's own `created: true/false` (`201`/`200`) convention exactly, extended with an `engagement` field in the response.

### 3.7 Privacy-safe location handling — the design decision the mandate flagged as high-risk

Resolved in-repo, not escalated (§11.1 explains why this did not need a Conflict Escalation). `ServiceRequest` stores **only** `locationLabel` (free text, "Bairro, Cidade/UF", the exact same shape and precision as `marketplace_listings.location`, which every Partner-posted anúncio already exposes publicly today) and an optional `radiusKm` **integer preference** — no latitude/longitude column exists anywhere in `service-request.schema.ts`.

**Correction applied after independent Diff Review (§J.2 of `IP-003-DIFF-REVIEW.md`)**: the original version of this section, and its copies in `service-request.ts`, `service-request.schema.ts`, migration 0030's header comment, `docs/event-catalog.md`, `docs/openapi.yaml`, and `CLAUDE.md`, stated "no Partner coordinate data exists anywhere in the repo." **That premise is false.** `marketplace_order_execution_events.latitude/longitude` (migration `0017_aromatic_vivisector.sql`, PACK-03 baseline) stores real Partner-side GPS captured during field-execution check-in/checkout — independently confirmed by the reviewer via `grep -rniE "\blatitude\b|\blongitude\b"` across `apps/api/src` and `apps/api/drizzle`, and re-confirmed here. The **actual code decision remains correct**: this per-event, post-hoc GPS data cannot support prospective, pre-engagement distance matching — it is captured only after an order has already progressed to field execution, is scoped to a single execution event (not a durable Partner "service area" or "home base"), and repurposing it for matching would require materially new aggregation infrastructure (deriving and maintaining a per-Partner service-location profile from historical execution events) that does not exist and is out of this IP's minimum-safe scope. The two facts that actually justify the design decision are:

1. `MarketplaceListingRepository.search()`'s own `location` filter is **already** free-text `ilike`, with zero lat/lng/radius support anywhere in the `marketplace_listings` schema (IP-000 §14, IP-015 row: "location is free-text ilike with no lat/lng/radius query" — an acknowledged, explicitly out-of-scope-for-now gap, not something this IP is asked to fix). Storing a Member's precise coordinates while having no **pre-engagement, matchable** Partner location profile to compare them against would add a privacy-sensitive data column with zero matching functionality gained — the worst possible trade-off.
2. Genuine geometric radius matching requires a durable, per-Partner service-location profile — not a one-off execution-event geotag — and no such profile exists anywhere in this repository (`marketplace_listings` itself has no lat/lng column either, and no aggregation layer turns execution-event geotags into a Partner "base"). Building that infrastructure (Partner service-area geocoding, a profile table, distance queries) is a materially larger addition than "the minimum safe design that satisfies this IP" and squarely belongs to IP-005 (Scheduling, Availability, **Location** & ETA) per the Manifest's own IP list — not invented here.

`radiusKm` is captured and persisted (the spec explicitly names "radius" as a constraint the Member describes) as a forward-compatible preference for IP-005 to give real geometric meaning to later, but is **not** used to filter or rank matches in this IP — matching (§3.3) uses `locationLabel` text + category + trust level, exactly mirroring MRK-004's own existing precision level. This is documented here, in the migration's own header comment, and in `service-request.ts`'s top-of-class comment (now corrected in all six locations, §11.7), specifically so a future reader does not mistake the unused `radiusKm` column for a solved problem, and does not mistake this correction for a claim that the underlying design was wrong.

## 4. Not implemented / out of scope

Per the IP-003 spec's explicit Out of Scope (§4) and this program's non-negotiable constraints:
- **No semantic/vector search** — matching (§3.3) is a parameterized SQL query against existing indexed columns; zero embedding/vector/LLM code anywhere in the diff.
- **No autonomous AI selection** — the Member always makes the final engagement decision by calling `POST .../engage` with an explicit `listingId`; the system never auto-selects or auto-contacts a Partner on the Member's behalf.
- **No rebuild of the existing listing/conversation/proposal/order flows** — `marketplace-listing.ts`, `marketplace-conversation.ts`, `marketplace-offer.ts`, `marketplace-order.ts`, and every one of their use cases/controllers/repositories are untouched (confirmed by `git diff --stat`, §5 — zero lines changed in any of those files).
- **No scheduling/calendar system** — `urgency` (enum) + optional `preferredDate` (a single nullable timestamp) is the entire timing model; there is no availability window, no recurring schedule, no ETA computation. That is explicitly IP-005's job.
- **No geometric radius/geocoding infrastructure** — see §3.7.
- **No Partner-facing "browse open requests" endpoint.** Discovery is always Member-initiated (`GET /marketplace/service-requests/{id}/matches`, owner-only) — there is no route that lets a Partner list Members' open needs. This is a deliberate scope boundary, not an oversight: the acceptance criteria's wording ("Member can create a service need; eligible Partners can be discovered/targeted") reads naturally as the Member doing the discovering/targeting, and a Partner-facing request board would be a materially larger, more privacy-sensitive feature (broadcasting a Member's stated need to arbitrary Partners) that the mandate's own privacy framing argues against building without an explicit product decision. Flagged for the reviewer in §16, not silently decided.
- **No frontend work** — IP-000 §3.7 confirmed the Marketplace module's own baseline listing/conversation UI already exists in `apps/web`, but no Member/Partner role split or dedicated journey exists yet (that is IP-016/017's job). This IP is backend-only, consistent with IP-007's own precedent and with no `apps/web` file being named anywhere in the mandate.
- **No modification of `apps/api/src/modules/payment/**`** — confirmed zero files touched in that directory.
- **No retrofit of `MarketplaceListingRepository.search()`'s `sort=relevance` no-op** — that is IP-015's explicitly-scoped gap (IP-000 §14), not silently fixed as a side effect of reusing the method here.

## 8. Security / authorization / privacy

- **Every route requires authentication**; none is `@Public()` — confirmed by reading the controller directly (no `@Public()` decorator anywhere in `marketplace-service-request.controller.ts`).
- **Ownership enforced at the use-case layer, not just the domain layer, and as 404 rather than 403**: every read/write use case (`GetServiceRequestUseCase`, `DiscoverServiceRequestMatchesUseCase`, `EngageServiceRequestUseCase`, `CloseServiceRequestUseCase`, `CancelServiceRequestUseCase`) checks `!request || !request.isOwnedBy(actorId)` and throws `ServiceRequestNotFoundException` (404) — deliberately **not** `ServiceRequestOwnershipException` (403) — so that a non-owner cannot even confirm another Member's request exists. This is a stricter posture than `MarketplaceOrder`'s own `assertParticipant` → 403 pattern, chosen because a `ServiceRequest` (unlike an `Order`, which both parties know about because they negotiated it) has no legitimate second reader — nobody but the owner should ever learn it exists. `ServiceRequest.assertOwner()`/`close()`/`cancel()` still throw the 403 domain exception as defense-in-depth (never actually reachable via the controller path, since the use case layer already filters by ownership first) — documented explicitly as intentional, not dead code, in `service-request.ts` and flagged for reviewer attention in §16.
- **Privacy (LGPD / Shared Standards §7 "do not expose precise location beyond product need")**: §3.7 is the core design decision here. No precise coordinates are stored or transmitted anywhere in this IP's schema/DTOs/responses. `locationLabel` is exactly as coarse as what every Partner already publishes today via `marketplace_listings.location`.
- **Purpose-bound / minimize collection**: the Member-facing detail response (`ServiceRequestResponse`) is never returned to anyone but the owner (§ above). The Partner-facing discovery response (`ServiceRequestMatchResponse`) carries only what `ListingSummaryResponse` already carries publicly today (MRK-004) — no new field of the Member's private request data (budget, exact description, preferred date) is ever exposed to a Partner through the matches endpoint; a Partner only learns "a Member engaged you" once an actual conversation/message exists (the same visibility a listing-page contact already has).
- Every new state transition is audited via the existing `AuditLogService.record()` — `CreateServiceRequest`, `EngageServiceRequestPartner`, `CloseServiceRequest`, `CancelServiceRequest` — matching the granularity of the equivalent MRK operations.
- No new PII beyond what the Member explicitly types into `title`/`description`/`locationLabel` — the same class of free-text the Member already types into a listing's own `description`/`location` fields today.

## 9. Data / financial invariants

- **No floating-point money** — `budgetMinAmount`/`budgetMaxAmount` use the exact same `numeric(18,2)` + `toFixed(2)`/`Number()` round-trip convention as `marketplace_listings.price` and `marketplace_offers.amount`; a dedicated domain assertion (`assertBudget`) rejects `budgetMinAmount > budgetMaxAmount` before the entity is ever constructed.
- **No mutation of any existing financial entity** — `Payment`, `TrustCustody`, `MarketplaceCommercialSnapshot`, `TrustChangeOrder` are all untouched; this IP creates no charge, no custody, no commercial snapshot. A `ServiceRequest` carries only a **budget hint** (optional, informational — never becomes an `Offer.amount` automatically; the Member/Partner still negotiate a real offer through the existing MRK-009..014 flow after engaging).
- **Idempotency on the one state-changing surface with real concurrency risk**: `markMatchedIfOpen` (CAS) + `saveEngagement` (`onConflictDoNothing()`, no target — §3.4) together guarantee that N concurrent engagements against the same `ServiceRequest` produce at most one `OPEN -> MATCHED` transition and at most one engagement row per `(serviceRequestId, listingId)` pair, proven by a genuine two-way concurrent e2e test (§10.3) exercising two *different* listings racing to be the first match. **This invariant now extends to the event layer, not just persisted state** — after the correction in §11.6, exactly one `ServiceRequest.Matched` outbox row is produced per genuine race, not one per racing caller; the e2e race test asserts this directly against `outbox_events` (§10.3), which the pre-correction version of this test did not do (an independent Diff Review found and this IP fixed a real double-publish defect at the event layer that coexisted with a correct persisted-state guarantee — see §11.6 for the full account).
- **Terminal states are genuinely terminal**: `CLOSED`/`CANCELLED` have empty transition-target arrays in `SERVICE_REQUEST_TRANSITIONS` — a second `close()`/`cancel()` call structurally throws `ServiceRequestTransitionException`, proven by both a unit test and an e2e test (§10.1, §10.3).
- Existing PACK-00..03/IP-001/002/007 invariants are all regression-tested green by the full suite (§10.3) — none of the files that encode those invariants were touched by this IP.

## 11. Deviations / decisions

1. **Resolved the location-privacy design question in-repo, did not escalate** (§3.7) — the task's own instructions flagged this as "the most likely candidate" for a Conflict Escalation. Preflight found this is **not genuinely ambiguous**: the repository already has a concrete, existing precedent for exactly this precision level (`marketplace_listings.location`, free-text, publicly exposed today) and a concrete, existing gap that makes geometric radius matching impossible to build honestly right now (no *pre-engagement, matchable* Partner location profile exists — see the corrected reasoning in §3.7 and the correction told in full in §11.7). Choosing "coarse free-text label, no coordinates stored at all" is not inventing a new privacy policy — it is declining to introduce a *new* precise-data column that the mandate explicitly warns against ("do NOT introduce precise lat/lng broadcast to arbitrary Partners") for zero functional gain, while still fully satisfying the letter of the spec ("category/location/radius/timing constraints" — `radiusKm` is captured as a declared preference, honestly not yet acted upon). This is the most privacy-conservative option, not the most feature-complete one, chosen deliberately.
2. **404, not 403, for a non-owner on every ServiceRequest route** (§8) — a stricter posture than `MarketplaceOrder`'s own precedent, justified because unlike an Order (which both a buyer and seller legitimately know about), a `ServiceRequest` has exactly one legitimate reader. Flagged for the reviewer (§16) as the one place this agent chose a *stricter* authorization posture than an existing in-module precedent, rather than copying that precedent verbatim. Independently re-verified by the Diff Review (§E) and confirmed correct.
3. **No Partner-facing "browse open requests" endpoint** (§4) — the acceptance criteria's exact wording ("eligible Partners can be discovered/targeted") was read as Member-initiated discovery, not a Partner-facing feed. Judged that building the latter without an explicit product decision would itself risk exactly the kind of privacy overreach the mandate warns about (broadcasting a Member's stated need widely) — flagged for the reviewer to specifically re-judge this scope boundary. Independently re-judged by the Diff Review (§J.5) and confirmed sound.
4. **`EngageServiceRequestUseCase` runs in two transactions, not one** (§3.5) — `ContactListingOwnerUseCase` manages its own transaction internally and was deliberately left with **zero** modification (the mandate's strongest instruction: reuse its shape, don't touch it). The engagement bookkeeping (CAS transition + engagement row + two new events) runs in a second transaction immediately after. If the second transaction fails, the conversation from the first transaction remains valid (the Member already has a real contact) and a retry of the whole `engage` call is **safe for persisted state** (`ContactListingOwnerUseCase` reuses the same conversation; `saveEngagement`/`markMatchedIfOpen` do not duplicate rows or transitions). This mirrors the exact eventual-consistency posture IP-007 §12.2 already documented and accepted for an analogous two-step flow (Change Order approval → incremental authorization). **Caveat identified by the Diff Review (§F, MINOR/OBSERVATION, §J.3)**: this retry is *not* fully idempotent end-to-end at the conversation layer — `ContactListingOwnerUseCase` always creates a new message, even when reusing an existing conversation, so a crash-triggered retry between the two transactions appends one extra, duplicate-content message. This is pre-existing MRK-006 behavior, not introduced by this IP, and is arguably the safer trade-off (an extra message vs. a lost contact) — but the original wording here overstated the retry as unqualifiedly "idempotent." Corrected in the code comment (`engage-service-request.usecase.ts`'s class doc) and here: the state (status, engagement row, event count) is idempotent on retry; the conversation's message history is not.
5. **`budgetMinAmount`/`budgetMaxAmount` use `numeric(18,2)` reais, not integer cents** — deliberately matches the Marketplace module's own existing money convention (`marketplace_listings.price`, `marketplace_offers.amount`), not the Payment module's cents convention. A `ServiceRequest`'s budget is a non-binding hint, never itself charged or custodied — it is not "money" in the PAY-0xx sense this repository's cents convention exists to protect; it is the same class of value `MarketplaceListing.price` already is.
6. **Correction (post-review): `ServiceRequest.Matched` double-publish under genuine concurrency (Diff Review §F/§J.1, MAJOR)** — told in full for transparency, matching this program's standard of disclosing real defects found, not just intentions. The independent Diff Review found that `EngageServiceRequestUseCase` gated the `ServiceRequest.Matched` outbox enqueue on a **stale pre-transaction read** (`wasAlreadyMatched = request.status === MATCHED`, computed from a `findById()` call made before `ContactListingOwnerUseCase` ran and before the database transaction opened) rather than on `markMatchedIfOpen`'s own CAS return value. The persisted `service_requests.status` transition was, and remains, correctly CAS-protected — proven clean across multiple independent race-test runs both before and after this fix — but under a genuine two-way race (two concurrent `engage()` calls against different listings, both reading `OPEN` before the race window), **both** callers could independently decide `wasAlreadyMatched = false` and **both** would enqueue `ServiceRequest.Matched`, producing two event rows for a transition that happened once. No current consumer subscribes to this event (confirmed: `docs/event-catalog.md`'s own entry states "Consumidores: nenhum hoje"), so there was no live user-visible symptom, but it directly contradicted this report's own explicit correctness claim and would have surfaced as a duplicate notification the first time IP-013 wires up a consumer. **Fix**: capture `markMatchedIfOpen`'s boolean return value in a local (`casWon`) and gate the `ServiceRequest.Matched` enqueue on that value instead — the exact idiom `apps/api/src/modules/payment/application/usecases/release-funds.usecase.ts` (IP-007) already uses for its own two CAS calls. **New test coverage added**: a unit test in `engage-service-request.usecase.spec.ts` ("corrida: request lida como OPEN mas a CAS é perdida") that mocks `markMatchedIfOpen` returning `false` while the request is read as `OPEN`, asserting `ServiceRequestEngagement.Created` is published but `ServiceRequest.Matched` is not; and, in the existing e2e race test, two new `outbox_events` assertions — exactly one `ServiceRequest.Matched` row and exactly two `ServiceRequestEngagement.Created` rows after the real two-way race — which is precisely the class of assertion the Diff Review noted the original test lacked (it only checked final `status` and engagement-row counts, never the outbox). Both the new unit test and the re-run e2e race test pass after the fix (§10).
7. **Correction (post-review): overstated location-privacy premise (Diff Review §F/§G/§J.2, MAJOR)** — also told in full. The original §3.7 (and its copies in `service-request.ts`, `service-request.schema.ts`, migration 0030's header comment, `docs/event-catalog.md`, `docs/openapi.yaml`, and `CLAUDE.md`) stated "no Partner coordinate data exists anywhere in the repo." **This was factually wrong.** `marketplace_order_execution_events.latitude/longitude` (migration `0017_aromatic_vivisector.sql`, PACK-03 baseline) stores real Partner-side GPS captured during field-execution check-in/checkout — the Diff Review found this via an independent repo-wide `grep -rniE "\blatitude\b|\blongitude\b"` rather than trusting this report's claim, exactly the kind of verification this program expects. Only the stated *reasoning* was inaccurate. **Fix**: corrected the claim in all six locations (§3.7 above, plus `service-request.ts`, `service-request.schema.ts`, migration 0030, `docs/event-catalog.md`, `docs/openapi.yaml`, `CLAUDE.md`) to the precise version: no *pre-engagement, matchable Partner service-location profile* exists — the only Partner-side coordinates in this repository are post-hoc field-execution-event geotags, which cannot serve prospective matching without new aggregation infrastructure. This is a documentation/reasoning-integrity correction, not a code change beyond comments — confirmed by `git diff` that the fix touches only comments/docs, no schema, no query, no DTO shape.
