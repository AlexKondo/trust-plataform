## 2. The migration (`0033_ip005_scheduling_availability_location_eta.sql`) — highest-risk item, read in full — SAFE

Read the migration file end to end, plus `marketplace-order.schema.ts`'s new index definition and the Drizzle Postgres migrator (`shared/database/migrate.ts`, uses `drizzle-orm/postgres-js/migrator`, which applies each migration file's statements inside a single DB transaction).

- **The exact swap INCONSISTENCIAS #26 prescribed**: `DROP INDEX IF EXISTS idx_marketplace_scheduling_order` followed by `CREATE UNIQUE INDEX IF NOT EXISTS idx_marketplace_scheduling_order_active ON marketplace_order_schedulings (order_id) WHERE status = 'ACTIVE'`. Confirmed textually identical in intent to INCONSISTENCIAS #26's own words ("trocar por `UNIQUE(order_id) WHERE status = 'ACTIVE'`").
- **Existing-row safety, verified by my own reasoning, not the report's**: before this IP, `idx_marketplace_scheduling_order` was an **unconditional** `UNIQUE(order_id)` index — meaning every order in the database already had **at most one** `marketplace_order_schedulings` row, full stop, regardless of its `status` (`ACTIVE` or `CANCELLED`). A partial index that only enforces uniqueness among `status='ACTIVE'` rows is trivially satisfied by any table where every `order_id` already appears at most once in total. **No backfill is needed and none is possible to get wrong**: there is no scenario, under the pre-migration constraint, where two rows for the same order could both be `ACTIVE` after this migration applies — the old constraint already made that geometrically impossible before this IP touched anything. This directly answers the assignment's specific concern ("could two existing rows for the same order both end up ACTIVE") — no.
- **Ordering / transactional safety**: the `DROP INDEX` + `CREATE UNIQUE INDEX` pair executes inside the same migration-file transaction as every other statement in `0033`. Postgres DDL is transactional; a concurrent session cannot observe an intermediate state where neither index exists (it sees pre-migration state until commit, then post-migration state), and any concurrent write attempting to touch `marketplace_order_schedulings` during the `DROP INDEX`/`CREATE INDEX` statements (both take `ACCESS EXCLUSIVE` locks on the table briefly) blocks until the migration transaction commits or rolls back — there is no unprotected window. This is not applied to any shared/prod environment by this IP (confirmed: only exercised against embedded/ephemeral test Postgres instances), so the point is about the migration's *general* safety for eventual real application, not about anything executed against real data.
- **`cancelled_reason` column**: nullable, `ADD COLUMN IF NOT EXISTS`, no data migration — every existing row gets `NULL`, correctly meaning "not a reschedule." Verified this is additive and non-destructive.
- **New tables** (`marketplace_partner_availability_windows`, `marketplace_order_travel_statuses`): both `CREATE TABLE IF NOT EXISTS` with guarded (`DO $$ IF NOT EXISTS`) FK addition — matches the established 0024–0032 idiom, confirmed by spot-reading two prior migrations in the same style.

## 3. The `saveScheduling` upsert-target change (`orderId` → `id`) and the reschedule write path — CONFIRMED CORRECT

Read `drizzle-marketplace-order.repository.ts::saveScheduling`, `manage-order.usecase.ts::schedule/reschedule/cancel`, and `order-lifecycle.service.ts::commit` in full (not excerpts).

- The conflict target change is necessary and correctly reasoned: Postgres cannot resolve `ON CONFLICT (order_id)` against a table whose only unique constraint on `order_id` is now partial (`WHERE status='ACTIVE'`) without repeating the exact predicate in the `ON CONFLICT` clause. Targeting the row's own primary key (`id`, always unique) sidesteps this correctly for both call shapes that exist: (a) insert a brand-new row (fresh `id`, no conflict, plain insert) and (b) update an existing row in place (same `id`, conflict resolves to update) — this is exactly what `schedule()` (new insert), `cancel()` (existing-row update), and `reschedule()` (one of each) do.
- **`reschedule()`'s two-write sequence is correctly ordered within a single transaction.** `OrderLifecycleService.commit()` wraps `orderRepository.save`, `alsoInTransaction`, the outbox enqueue, and the audit write inside one `this.db.transaction(async (tx) => {...})` call (`order-lifecycle.service.ts` lines 98–128) — genuinely one DB transaction, not merely sequential awaits. Inside `reschedule()`'s `alsoInTransaction`, the code `await this.orderRepository.saveScheduling(current, tx)` (the **old** row, now `CANCELLED`) executes **before** `await this.orderRepository.saveScheduling(next, tx)` (the **new** row, `ACTIVE`). Because the partial unique index is checked immediately after each statement (not deferred), this ordering means: at the moment the new `ACTIVE` row is inserted, the old row has already been demoted out of the `WHERE status='ACTIVE'` partial index's domain — so there is never an instant, even within the same transaction, where two `ACTIVE` rows for the same order coexist. Reversing this order (insert-new-then-cancel-old) would have been a genuine bug; the actual code does not do that.
- **`mrk-015-022.e2e.spec.ts` (pre-existing scheduling suite, untouched by this IP) — re-run independently, in isolation: 4/4 passed, 33.78s.** This is real, independently reproduced confirmation that the constraint swap and the upsert-target change do not regress the original `schedule()`/conflict-detection/cancel behavior.
- **`ip-005-scheduling-availability-location-eta.e2e.spec.ts` — re-run independently, in isolation: 5/5 passed, 32.90s**, including the direct DB assertion (per the report) that a rescheduled order ends with exactly 2 scheduling rows, exactly 1 `ACTIVE`.

## 4. Concurrent-reschedule race — independently reasoned through, not present

This was the assignment's specific area of highest scrutiny. Traced the full path for two `reschedule()` calls racing on the *same* order:

Both callers read `current` (the same `ACTIVE` row, id `X`) via `findLatestSchedulingByOrder` **before** either transaction opens — this is an application-level read, not locked. Each then opens its own DB transaction via `OrderLifecycleService.commit()`. Inside each transaction, the first write touching the scheduling table is `saveScheduling(current, tx)`, an `INSERT ... ON CONFLICT (id) DO UPDATE` against the **same row id `X`** — this necessarily takes a row-level lock on `X` (both transactions target the identical primary key). Whichever transaction acquires it first proceeds: updates `X` to `CANCELLED`, then inserts its own new row (`Y1`, `ACTIVE`), then commits, releasing the lock. The second transaction was blocked on the row-`X` update until the first committed; when it resumes (under READ COMMITTED), its own `UPDATE` on `X` succeeds (already `CANCELLED`, harmless re-write), but its subsequent `INSERT` of its own new row (`Y2`, `ACTIVE`) now collides with the partial unique index — `Y1` is already a committed `ACTIVE` row for the same `order_id`. This raises a genuine Postgres `23505` unique-violation **inside** the second transaction, which aborts and rolls back the *entire* second transaction atomically (including its own `UPDATE` on `X` and the order-status write) — Postgres does not partially commit an aborted transaction.

**Net result of the race: the loser's reschedule fails cleanly with no partial state; the winner's reschedule is the only one ever persisted.** This is exactly the DB-level backstop the report claims, and it is real, not asserted. The `23505` → HTTP 409 mapping is a real, generic, pre-existing mechanism (`global-exception.filter.ts`, `isUniqueConstraintViolation`, checks `postgres.PostgresError.code === '23505'` including the wrapped-`cause` case) — confirmed by reading the filter directly; this is documented, pre-existing technical debt (Shared Standards §13) that this IP does not introduce, it merely benefits from it correctly. **No BLOCKING race exists.** The application-level pre-checks (`findActiveSchedulingsForSeller`, `fitsAvailability`) are best-effort UX (same posture the original `schedule()` already had); the database constraint, not the pre-check, is what actually prevents the double-`ACTIVE` state, and it does so correctly under concurrency.

## 5. Partner availability windows (`PartnerAvailabilityWindow`, `fitsAvailability`) — read in full

- **Zero-windows-declared ⇒ zero restriction, confirmed by code, not just claim**: `fitsAvailability()` (`availability.service.ts` line 64) returns `true` unconditionally when `windows.length === 0`, before any date/timezone math runs. This is the first line of the function — there is no path by which a Partner with no declared windows can be blocked. Confirmed by the report's own e2e scenario and independently re-run (§3 above).
- **Timezone math, judged directly**: `localInstant()` uses `Intl.DateTimeFormat` with an explicit `timeZone` option to derive weekday + minute-of-day from a UTC `Date`, for the *specific instant* being converted — this correctly accounts for DST and historical offset changes (ICU resolves the offset for the given instant against the named zone's rules, not a cached/fixed offset), which is the class of bug a naive `getUTCHours() + offsetMinutes` approach would get wrong. Verified the weekday-index mapping (`Sun:0..Sat:6`) matches `PartnerAvailabilityWindow.dayOfWeek`'s own documented convention (same as `Date#getDay()`).
- **Midnight-crossing edge case, traced by hand**: a scheduled window starting Saturday 23:50 local and ending Sunday 00:10 local (`end.minuteOfDay = 10`, nonzero, `end.dayOfWeek !== start.dayOfWeek`) hits the `if (end.minuteOfDay !== 0 && end.dayOfWeek !== start.dayOfWeek) return false` guard and is correctly rejected — matches the documented "conservative, no cross-midnight semantics" design. A window ending **exactly** at local midnight (`end.minuteOfDay === 0`, next calendar day) is deliberately special-cased to `endMinuteOfDay = 1440` and compared against the *start day's* windows — this correctly allows a window like "22:00–24:00" to match a scheduled slot ending precisely at midnight without miscounting it as spanning two days. Both branches were read directly in `availability.service.ts` lines 70–77 and are logically sound; this is a genuinely conservative, not silently-wrong, implementation.
- **`PartnerAvailabilityWindow.overlaps()`** (half-open `[start,end)` interval intersection) is standard and correct; `assertNoOverlap()`'s O(n²) pairwise check is appropriate at the declared `max(30)` windows bound (zod-enforced in `setPartnerAvailabilityRequestSchema`).
