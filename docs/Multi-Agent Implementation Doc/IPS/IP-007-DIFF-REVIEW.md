## F. Concurrency/idempotency review

**The `onConflictDoNothing()` fix and the additive-only `ReleaseFundsUseCase` diff were the two highest-scrutiny items in this review — both verified line-by-line, not taken on faith.**

- **Migration constraints, read directly**: `0029_ip007_incremental_payment_authorization.sql` lines 81/83 create `idx_payment_incremental_authorization_change_order` (UNIQUE on `change_order_id`) and `idx_payment_incremental_authorization_idempotency` (UNIQUE on `idempotency_key`) as two **separate** unique indexes on the same table. Since `idempotencyKey = incremental-auth:{changeOrderId}` is deterministically derived from `changeOrderId` (confirmed in `create-incremental-authorization.usecase.ts`), the two constraints always collide together under a race — this independently confirms the report's root-cause diagnosis for the bug it found and fixed (§10.4 of the Completion Report), rather than taking the report's prose at face value.
- **The fix, read directly**: both `DrizzlePaymentIncrementalAuthorizationRepository.create()` and `DrizzleIncrementalTrustCustodyRepository.create()` call `.onConflictDoNothing()` with **no `target` argument** — confirmed by reading the actual method bodies. A target-less `ON CONFLICT DO NOTHING` suppresses a conflict on *any* unique/exclusion constraint on the table, which is the correct semantics here (either constraint colliding must produce the same "did not insert a duplicate" outcome). This was re-verified live: the e2e race test ("corrida: duas entregas concorrentes...") was run 4 independent times (once inside the full suite, three times in isolation) and never threw a raw `PostgresError`; every run resolved to exactly one `AUTHORIZED_AND_HELD` and one `SKIPPED{reason:'CONCURRENT_WINNER'}`/`ALREADY_PROCESSED`, with exactly one row in each of the two new tables.
- **`ReleaseFundsUseCase.prepare()`/`finalize()` additive-only claim, verified by reading the actual `git diff`** (not the Completion Report's description of it): every existing branch of `prepare()` (the `NO_CUSTODY`, `ALREADY_RELEASED`, `ALREADY_READY`, `DENIED` ×2, `READY` returns) is unchanged in its core logic — the only change per branch is a trailing `...(incremental ? { incremental } : {})` spread appended to the return object. `finalize()`'s pre-existing body was extracted verbatim into a new private `finalizeOriginal()` (identical statements, identical order; the only textual diff is `custodyId` → `custody.id`, a cosmetic consequence of the extraction, not a behavior change) with a new `finalizeIncremental()` branch added alongside via a `findById` fallback chain. This matches the report's "additive-only, byte-identical for existing paths" claim exactly.
- **`custody-release.usecase.spec.ts`'s diff, verified by reading it in full**: the only changes are a new `noIncrementalTranches()` mock helper and one added constructor argument at two `new ReleaseFundsUseCase(...)` call sites — zero assertions were touched. This makes the claim "21 pre-existing tests pass unchanged" structurally sound by construction (the mocks return empty/no-op values that make `prepareIncrementalTranches` return `undefined` and `finalize()`'s `incrementalCustodyRepository.findById` fallback return `null`, so every pre-existing code path executes identically) — and was independently confirmed passing in the full reproduced unit-suite run (48 files / 408 tests, exact match, §I).
- **`evaluateIncrementalRelease` vs. `evaluateRelease`, traced independently**: `evaluateRelease`/`snapshotMatches` are byte-for-byte unchanged (confirmed: the diff shows zero modifications to that code region, only a new function appended after it). The new function replaces `snapshotMatches`'s value-equality check with a belonging check (`trancheBelongsToPayment`) — correct given a tranche is, by design, never equal in amount to the whole Payment. The deliberate tolerance of `Payment.status === FUNDS_RELEASED` (in addition to `FUNDS_IN_CUSTODY`) was traced end-to-end against `PAYMENT_TRANSITIONS` (`payment-types.ts`): `FUNDS_RELEASED` has no outgoing self-transition and is only ever reached via a successful `finalizeOriginal()` call. Since `finalizeIncremental()` never calls `payment.transitionTo(...)`, and a failed/denied original release never sets `FUNDS_RELEASED`, this tolerance cannot admit releasing an incremental tranche after the original has failed or is in an inconsistent state — it only ever fires when the original tranche has *already completed successfully*, which is exactly the scenario the report's own §16.2 asked this review to specifically re-judge. No defect found; the design is sound.
- **Release-side race, re-run independently 4×** ("corrida: duas liberações concorrentes..."): every run produced `['ALREADY_RELEASED', 'RELEASED']` (sorted) with exactly one `Funds.Released` event for the tranche — the CAS write (`markReleasedIfReady`, `UPDATE ... WHERE status='READY_FOR_RELEASE' RETURNING`) genuinely serializes the two concurrent `finalize()` calls; no flake observed across 4 independent executions of this specific test.
