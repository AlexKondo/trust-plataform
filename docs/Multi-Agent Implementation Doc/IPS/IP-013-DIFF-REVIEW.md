## F. The `ServiceRequest.*` non-coverage reasoning — traced end-to-end, independently

This was the single highest-scrutiny item in this review, per the task brief's explicit instruction. Read the full call chain directly, not from prose:

1. **`EngageServiceRequestUseCase.execute()`** (`engage-service-request.usecase.ts:94-100`) calls `this.contactListingOwnerUseCase.execute(memberId, body.listingId, { message: body.message }, meta)` **unconditionally, on every single `engage()` call** — not just the first. This is a real, unconditional call, not a conditional "only if new conversation" branch.
2. **`ContactListingOwnerUseCase.execute()`** (`contact-listing-owner.usecase.ts:110-123`) **always** enqueues `MarketplaceMessage.Sent` with `payload.recipientId = listing.ownerId` — this line runs unconditionally in every call, regardless of whether the conversation was newly created or reused (only the `MarketplaceConversation.Created` event is conditional on `created`).
3. **`listing.ownerId`** is the exact same value used as `partnerId` in `EngageServiceRequestUseCase`'s own `engagementRecord.partnerId` (`engage-service-request.usecase.ts:109`) and in the `ServiceRequestEngagement.Created` payload's `partnerId` field — confirmed by direct read, not inference.
4. **`ntf.message-sent`** (pre-existing, `notification-rules.ts:136-146`) fires on `MarketplaceMessage.Sent` and notifies exactly `str(payload, 'recipientId')`.

**Conclusion: the chain is real and unconditional.** Every `engage()` call — not merely the first — causes the Partner to receive `MESSAGE_RECEIVED` via the pre-existing rule, in addition to the new `SERVICE_REQUEST_ENGAGEMENT_RECEIVED` notification this IP adds for request-specific context. The report's claim is accurate, and independently reproduced live by this IP's own e2e test #1 (§H).

**However, `ServiceRequest.Closed`/`.Cancelled` leave a real, disclosed gap for an already-engaged Partner.** Read `resolve-service-request.usecase.ts` in full: both `CloseServiceRequestUseCase` and `CancelServiceRequestUseCase` publish payloads containing only `{ serviceRequestId, memberId, previousStatus, [reason,] closedAt/cancelledAt }` — **no `partnerId`, no list of engaged Partners anywhere in the payload.** If a Member closes or cancels a `ServiceRequest` after having engaged one or more Partners (an active conversation already exists), none of those Partners receive any notification that the underlying request is now closed/cancelled — they only find out if they happen to check the conversation or ask. This is a real, defensible product gap, not a code defect:
- The report explicitly discloses it (§11.4) and flags it for reviewer re-judgment rather than hiding it.
- Building it correctly would require a new DB-backed lookup of `service_request_engagements` by `serviceRequestId` inside the consumer (the payload alone cannot answer "who is engaged") — which conflicts with this IP's own "payload-only, no business logic inside notification consumers" pattern (spec §4) and would be a materially larger change than the table-driven "minimum safe design" this IP otherwise delivers correctly.
- The actor-exclusion rule ("quem age nunca é avisado do próprio ato", `CLAUDE.md:31`) is about not notifying the *acting* Member of their own act — it does not, on its own, cover whether a *third party* (an engaged-but-not-acting Partner) should be told. The report's framing conflates these two justifications slightly; the real reason this is acceptable for MVP is the architectural cost of the lookup, not the actor-exclusion rule itself.

**Verdict on this finding: MINOR.** Non-blocking. A legitimate, disclosed scope trim with a real architectural reason, not an oversight — but it is a genuine (if narrow) product gap that should be tracked as follow-up, not silently considered "fully closed."

## J. Findings

Classified CRITICAL / BLOCKING / MAJOR / MINOR / OBSERVATION.

1. **MINOR — `ServiceRequest.Closed`/`.Cancelled` leave an already-engaged Partner without any notification.** See §F. A real, narrow, disclosed product gap: an engaged Partner who has an active conversation about a `ServiceRequest` is not told when the Member closes or cancels it. The current event payloads (`{serviceRequestId, memberId, previousStatus, [reason]}`) do not carry a `partnerId`/engaged-partner list, so closing this gap correctly would require a new DB-backed lookup inside the notification consumer — a real architectural step up from this IP's otherwise-consistent "payload-only" pattern, not a one-line fix. Recommend tracking as explicit follow-up scope (e.g., under a future IP or an approved change request), not silently treating this family as "fully closed" per IP-003's own "notificação ao Member/Partner é escopo do IP-013" framing.
2. **MINOR — Completion Report §10.3's "clean on the first run, no retry needed" framing should not be read as the pre-existing e2e timing-flake class being resolved.** This reviewer's independent first run hit the identical flaky file/symptom (`ip-002-i18n.e2e.spec.ts`, trust-score poll-window timeout) documented four times across `IP-003-DIFF-REVIEW.md`. Confirmed transient (clean on isolated retry), not a regression — but the class of flakiness is still present in this environment and unrelated to this IP's diff either way.
3. **OBSERVATION — the `Identity.PasswordChanged`/`.PasswordRecoveryRequested` self-notification is a correct, deliberate exception to the literal actor-exclusion rule, not a violation.** `CLAUDE.md:31`'s rule ("quem age nunca é avisado do próprio ato") is written for the *no-spam* case (e.g., "you accepted this offer" is a useless notification to the accepter). Password-change/recovery notifications are categorically different: they are a security control whose entire value depends on reaching the account owner regardless of who performed the action — if it genuinely was the account owner, the notification is a confirmation/audit trail; if it was an attacker with a stolen session or a recovery request the owner didn't make, the notification **is** the detection mechanism. This is the same pattern used by essentially every mainstream identity system (Google, GitHub, banks) and is explicitly reasoned about in the report (§8) and in `event-catalog.md`'s updated entries. Independently judged correct — not a rule violation, an appropriate domain-specific exception to a general-purpose anti-spam heuristic.
4. **OBSERVATION — the Brevo/`notification`-module disconnection claim is fully verified.** `grep -rn "brevo\|Brevo" apps/api/src/modules/notification` independently re-run: zero matches. `identity.module.ts:72-78` confirmed Brevo is genuinely wired (with graceful `LoggingEmailService` fallback keyed on the `xkeysib-` REST key prefix) but scoped entirely to `identity`'s own two transactional flows. The scope decision not to extend it into the generic `notification` module is reasonable and correctly flagged as a product/architecture decision rather than silently either built or dropped.
5. **OBSERVATION — the two self-reported test-authoring bugs are genuinely test-only, confirmed independently.** `auth.controller.ts:100-101` decorates `changePassword` with `@HttpCode(HttpStatus.NO_CONTENT)` — the route genuinely returns 204, confirmed by direct read of the controller (not just the report's claim), and the e2e test asserts `expect(changed.statusCode).toBe(204)` correctly. Note: `docs/openapi.yaml` does not document `/auth/change-password` at all (no path entry found by grep) — this is a **pre-existing** documentation gap, not introduced or touched by this IP, and out of this IP's scope to fix; noted for completeness, not held against this IP. The custody-wait fix in the `hourlyContractInProgress` test helper (`ip-013-...e2e.spec.ts:264-278`) matches the exact pattern of IP-007's own `contractInProgress` helper — confirmed by reading both; a genuine test-authoring gap, not a production-code symptom.

No CRITICAL finding. No BLOCKING finding — the two MINOR items are disclosed, scoped, and do not compromise money, security, or data integrity; they do not require this IP to be reworked before merge, but should be tracked.
