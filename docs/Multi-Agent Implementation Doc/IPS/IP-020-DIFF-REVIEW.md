## 2. Finding-by-finding verification (report's own §16 focus list)

### 2.1 "No new table" design decision

Read `AnalyticsRepository` end to end (317 lines). Confirmed: every one of the 6 methods issues only `SELECT`s (zero `insert`/`update`/`delete`), reads Marketplace/Payment/Trust/Identity table definitions directly via Drizzle schema imports (not domain repositories, not other modules' providers), and every count/sum is recomputed on every call — no persisted analytics state anywhere. The on-demand design is a reasonable MVP choice given the spec's own "no enterprise data warehouse unless required by proven scale."

**OBSERVATION (worth noting, not blocking):** the report's own justification overstates the indexing story. It claims "every query in `AnalyticsRepository` is a single-table or two-table indexed aggregate... not a full-table scan," citing `idx_marketplace_order_status`/`idx_payment_authorization_status`/`idx_service_request_status` as evidence. Independently reading the actual index definitions (`marketplace-order.schema.ts`, `service-request.schema.ts`, `payment.schema.ts`) shows:
- `getFunnelCounts` builds each stage count as `count(*) filter (where date_col >= x and date_col < y)` **inside a `SELECT` with no top-level `WHERE` clause** — Postgres must visit every row of `service_requests`, `marketplace_offers`, `marketplace_orders`, and `trust_custodies` on every single call to `/admin/analytics/overview`, regardless of how narrow the requested date window is. This is a full-table scan by construction, not an index-optimized query — no index on a bare `created_at`/`completed_at`/`customer_confirmed_at`/`released_at` column would even help here, because the predicate never appears in a `WHERE`.
- The cited indexes (`idx_marketplace_order_status` on `status`) don't apply to these date-range predicates at all — they index a different column entirely.
- `getOutcomeCounts`/`getPaymentAuthorizationCounts` *do* use a real `WHERE gte(...)/lt(...)`, which is scan-restrictable in principle, but there is still no plain index on `marketplace_orders.created_at` or `payment_authorizations.created_at` alone (only composite `(buyerId, createdAt)`/`(sellerId, createdAt)`, which don't help an unfiltered date-range scan) — so these too fall back to a full sequential scan today.

At current MVP data volumes (tens to low hundreds of rows, per every prior IP's own evidence) this is harmless — every query ran in low tens of milliseconds during this review's e2e run. But it is a real trap for later: the query shape (FILTER-without-WHERE for the 4-stage funnel; WHERE-without-supporting-index for outcomes/payments) means adding rows will degrade linearly with total table size, not with the size of the requested window, and no amount of adding a `created_at` index today would fix `getFunnelCounts`'s specific shape without also restructuring the query. Flagging as OBSERVATION per the task's own instruction — does not need to block, but should be called out so it isn't silently taken as "already indexed and safe" going forward.

### 2.3 Privacy / PII-leak boundary

Read `AnalyticsRepository` in full. No query anywhere selects `identities.fullName`, `.email`, `trustPassports.phone`, address columns, or precise-location columns — every `select({...})` projects only `count`/`sum`/`level`/`deletedAt`(for filtering, not returned). The only individually-scoped column ever read is `trustPassports.documentVerified` (a boolean), which cross-checks cleanly against IP-021's own `data-classification.ts`: `trust_passports`'s `*_verified` booleans are explicitly documented there as preserved post-anonymization "historical fact, not PII itself" — never `verifications`/`verification_evidences` (classified `SENSITIVE_KYC_EVIDENCE`, `NOT_TOUCHED_ESCALATED`). The privacy boundary in this IP is consistent with, not a new definition of, IP-021's classification.

The e2e's negative-match assertions were independently inspected, not just trusted: they check the exact seeded `seller.email`/`buyer.email`/`seller.fullName`/`buyer.fullName`/`seller.identityId`/`buyer.identityId` strings (real values generated per-test-run, not fixed fixtures) against `JSON.stringify(body)` of the raw serialized response — this is a strong check, not a weak generic pattern match. The `trust-adoption`/`cohorts` tests additionally check `/@e2e\.trustplatform\.test/` against the whole response body, catching any e2e-seeded email domain leak generically. Confirmed correct and meaningful.

### 2.4 `Date`-in-raw-`sql` bug fix

Grepped the whole analytics module for `` sql` `` usage — exactly 2 raw-template sites (`getTimingMetrics`, `getCohortRetention`), both using `.toISOString()` on every interpolated `Date` (`range.from.toISOString()`, `range.to.toISOString()`, `cutoff.toISOString()`). `getFunnelCounts` computes `fromIso`/`toIso` once at the top of the method and uses those strings in every `sql<number>` fragment — no raw `Date` reaches a `sql` template anywhere. `getOutcomeCounts`/`getPaymentAuthorizationCounts` use `gte(column, value)`/`lt(column, value)` (column-typed Drizzle helpers, not raw `sql`), confirmed safe by design and by the full e2e run passing. No remaining raw-`Date`-into-`sql` site found anywhere in the module.

### 2.5 Admin-only authorization

`@UseGuards(AdminGuard)` is applied at the **class level** on `AnalyticsController` (`@Controller('admin/analytics')` + `@UseGuards(AdminGuard)`), covering all 3 current routes (`overview`, `trust-adoption`, `cohorts`) with no per-route decorator needed — and would automatically cover any future route added to this controller. `AdminGuard` itself (`admin.guard.ts`) is untouched (zero diff) — same mechanism used by `TrustScoreController`/`VerificationController`/`marketplace-review.controller.ts` (re-evaluates `identity.isAdmin` from the DB on every request via `IdentityRepository.findById`, never trusts the JWT payload). `JwtAuthGuard` is registered globally (`APP_GUARD` in `app.module.ts`), so `request.identity` is populated before `AdminGuard` runs — no route bypass path found; `AnalyticsModule` is registered normally in `app.module.ts`'s `imports` array alongside every other module, nothing unusual in ordering. Independently re-ran the 401/403 test (part of the full e2e run, §3) — passed.

## 4. Overall assessment

No CRITICAL, BLOCKING, or MAJOR finding. One MINOR-leaning-OBSERVATION on the indexing/performance reasoning (§2.1) — the design decision itself (on-demand SQL, no new table) is sound for this MVP, but the report's specific "these queries are already indexed" claim is not accurate for `getFunnelCounts` and is only partially accurate for `getOutcomeCounts`/`getPaymentAuthorizationCounts`. Recommend a follow-up note (not a blocker) for whoever revisits this when traffic grows: `getFunnelCounts` needs a top-level `WHERE` (or a per-stage query) plus supporting `created_at`/`completed_at`/`customer_confirmed_at`/`released_at` indexes before it will actually benefit from indexing.

All 6 of the report's own flagged-for-scrutiny items were independently re-verified and held up, most importantly the reconciliation e2e test, which was proven non-vacuous by a live deliberate-break-and-revert experiment.
